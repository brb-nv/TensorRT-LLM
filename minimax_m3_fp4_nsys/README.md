# MiniMax-M3-NVFP4 steady-state nsys profiling (ISL=8192 / OSL=1)

Minimal scripts to capture **steady-state** Nsight Systems profiles of
`MiniMax-M3-NVFP4` on an ISL=8192 / OSL=1 (prefill-dominated) workload, so you
can locate perf bottlenecks. One profile is produced per target concurrency.

The profile records **only** a window of steady-state engine iterations: the
benchmark runs warmup requests first, then the CUDA profiler is toggled on/off
around a fixed iteration window (`TLLM_PROFILE_START_STOP=A-B`) that nsys keeps
via `-c cudaProfilerApi`. Model load, CUDA-graph capture, warmup, and the
ramp/tail are all excluded, so each trace is small and clean.

## Files

| File | Role |
|------|------|
| `config.yaml` | trtllm-bench `--config` feature knobs (MSA sparse attention, fp8 KV cache, CUTLASS MoE). Validated NVFP4 path. |
| `gen_dataset.py` | Emits a tokenized `input_ids`/`output_tokens` JSONL of the requested ISL/OSL (auto-generated by `run_nsys.sh`). |
| `run_nsys.sh` | Profile one concurrency under nsys with steady-state capture. |
| `run_all.sh` | Sweep `run_nsys.sh` over several concurrencies (default: 1). |

## Prerequisites

- Inside the TensorRT-LLM container (`nsys`, `trtllm-bench`, `python3` on PATH).
- **>= 4 Blackwell (SM100+) GPUs, >= 140 GB each** — the default is `tp=ep=4`
  (the validated NVFP4 layout). MSA sparse attention needs SM100 + `fmha_sm100`.
- Model at `/home/scratch.trt_llm_data_ci/llm-models/MiniMax-M3-NVFP4`
  (override with `MODEL=...`).

## Run

```bash
# From the repo root. Default: concurrency 1.
bash minimax_m3_fp4_nsys/run_all.sh

# Full target sweep (concurrencies 1, 2, 4, 8, 16):
bash minimax_m3_fp4_nsys/run_all.sh 1 2 4 8 16

# A single concurrency directly:
bash minimax_m3_fp4_nsys/run_nsys.sh 8
```

Output per concurrency `N` lands in `out/cN/`:

```
out/cN/
  minimax_m3_fp4_cN.nsys-rep   <-- open in Nsight Systems
  report_cN.json               <-- trtllm-bench report (only if CAPTURE_END=stop)
  run_cN.log                   <-- full stdout/stderr
```

> By default the run uses `nsys --capture-range-end=stop-shutdown`: nsys tears
> `trtllm-bench` down the instant the steady-state window closes, so the run is
> short and never processes the full request set. A non-zero exit from the
> torn-down benchmark is **expected** — success is the `.nsys-rep` existing. Set
> `CAPTURE_END=stop` to let the benchmark run to completion instead.

## Inspecting a trace

```bash
# NVTX range summary (engine phases: _forward_step, _schedule, attention, MoE, ...)
nsys stats --report nvtx_sum --format table out/c1/minimax_m3_fp4_c1.nsys-rep

# Top CUDA kernels by total GPU time
nsys stats --report cuda_gpu_kern_sum --format table out/c1/minimax_m3_fp4_c1.nsys-rep
```

Or open the `.nsys-rep` in the Nsight Systems GUI.

## Tuning the steady-state window

The defaults (`WARMUP=5`, `NUM_REQUESTS=32`, `PROFILE_ITERS=12-24`) record a
short steady-state window a bit past the ramp, then `stop-shutdown` ends the
run — so a pass is quick and captures only steady-state work.

Confirm the window landed by checking `run_cN.log` for
`Profiling started at iteration 12`. If the log shows the run finished *without*
that line, the window was never reached — raise `NUM_REQUESTS` (or lower
`PROFILE_ITERS`). `NUM_REQUESTS` must exceed the window's stop iteration (the
script enforces this).

To record a longer/later window (and run the full request set):

```bash
CAPTURE_END=stop PROFILE_ITERS=40-80 NUM_REQUESTS=120 \
  bash minimax_m3_fp4_nsys/run_nsys.sh 16
```

### If it hangs (300s HangDetector hard-kill)

`--cuda-graph-trace=node` is a known deadlock source with NCCL collectives
captured in CUDA graphs (MoE expert-parallel all-to-all), so it is **off by
default**. Only enable it if you need kernels expanded inside CUDA graphs, and
expect possible hangs:

```bash
CUDA_GRAPH_TRACE=node bash minimax_m3_fp4_nsys/run_nsys.sh 1
```

If a run still hard-kills at ~300s (`Hang detected after 300 seconds`), the
executor loop stalled inside the profiled window. Try, in order: keep
`CUDA_GRAPH_TRACE` unset, drop `python-gil` from `--trace` in `run_nsys.sh`,
narrow `PROFILE_ITERS`, or profile at `concurrency 1` / the `triton` sparse path
first to isolate the trigger.

## Verifying piecewise CUDA graph

`config.yaml` enables piecewise CUDA graph for the context/prefill step
(`torch_compile_config.enable_piecewise_cuda_graph: true`,
`capture_num_tokens: [1, 8192]`). torch.compile splits the graph at attention
(MiniMax-M3 sparse attention is a registered piecewise boundary op) and captures
the non-attention pieces.

`run_nsys.sh` prints a `[verify]` summary at the end covering both sides:

1. **Capture** (from `run_cN.log`, emitted during startup/warmup):
   - Expect `Running piecewise CUDA graph warmup...` and
     `Run piecewise CUDA graph warmup for num tokens=8192` (and `=1`).
   - A `Skipping piecewise CUDA graph capture for num_tokens=[8192] ...` warning
     means the 8192 bucket exceeded the reachable ceiling and ran **eager** —
     raise `MAX_SEQ_LEN`/`MAX_BATCH_SIZE`.
2. **Replay** (from the trace — the window is post-warmup, so any graph launch is
   a replay):

   ```bash
   nsys stats --report cuda_api_sum --format table \
     out/c1/minimax_m3_fp4_c1.nsys-rep | grep -iE 'Name|cudaGraphLaunch'
   ```

   `cudaGraphLaunch` count > 0 ⇒ graphs are replaying in steady state.

**A/B check (recommended):** comment out `torch_compile_config` in `config.yaml`
and re-run. The prefill region should switch from `cudaGraphLaunch` (piecewise
on) to a long stream of `cudaLaunchKernel` with no context-piece graph launches
(piecewise off). In the Nsight GUI, the prefill iterations visibly collapse from
hundreds of individual kernel launches into a few graph launches when piecewise
is working.

> Note: `--cuda-graph-trace=node` would expand the kernels *inside* each
> piecewise graph in the timeline, but it is left off by default (deadlock risk
> with NCCL-in-graph). `cudaGraphLaunch` counts from `cuda_api_sum` are enough to
> confirm replay without it.

## Common overrides

| Env | Default | Notes |
|-----|---------|-------|
| `MODEL` | `.../MiniMax-M3-NVFP4` | Local HF model dir. |
| `TP` / `EP` | `4` / `4` | Must match available GPUs (world size = TP). |
| `ISL` / `OSL` | `8192` / `1` | Workload shape. |
| `MAX_SEQ_LEN` | `ISL+128` | Engine max sequence length. |
| `MAX_BATCH_SIZE` | `32` | Raise above your max concurrency. |
| `MAX_NUM_TOKENS` | `8192` | Prefill token budget per iteration. |
| `WARMUP` | `5` | trtllm-bench warmup requests (excluded from capture). |
| `NUM_REQUESTS` | `32` | Request supply; must exceed `PROFILE_ITERS` stop. |
| `PROFILE_ITERS` | `12-24` | Steady-state engine-iteration window recorded. |
| `CAPTURE_END` | `stop-shutdown` | nsys `--capture-range-end`; `stop` runs to completion. |
| `CUDA_GRAPH_TRACE` | _(unset)_ | `node` expands graph kernels (hang risk with NCCL-in-graph). |
| `NSYS_WAIT` | `primary` | nsys `--wait`; `primary` doesn't block on re-parented MPI workers at teardown. `all` waits for them. |

### The "re-parented processes" message is normal

On multi-GPU, `trtllm-bench` self-spawns the tp workers, which nsys sees as
*re-parented* processes. At `stop-shutdown` you'll see:

```
The target application terminated. One or more process it created re-parented.
Waiting for termination of re-parented processes.
```

This is the expected teardown. `NSYS_WAIT=primary` (default) keeps nsys from
blocking there. After it returns, confirm the report captured GPU work:

```bash
nsys stats --report cuda_gpu_kern_sum --format table out/c1/minimax_m3_fp4_c1.nsys-rep | head
```

If that shows kernels, the run is good. If the report has **no** CUDA kernels
(only host/API events from the client process), the self-spawned worker data
didn't make it into the combined trace — switch to the per-rank launch:

```bash
mpirun -n "${TP:-4}" \
  nsys profile -o out/c1/rank_%q{OMPI_COMM_WORLD_RANK} -f true \
    -t cuda,nvtx,python-gil -c cudaProfilerApi --capture-range-end=stop \
  trtllm-llmapi-launch \
  trtllm-bench --model "$MODEL" --model_path "$MODEL" throughput \
    --backend pytorch --config minimax_m3_fp4_nsys/config.yaml \
    --dataset minimax_m3_fp4_nsys/dataset_isl8192_osl1.jsonl \
    --tp 4 --ep 4 --max_seq_len 8320 --max_batch_size 32 --max_num_tokens 8192 \
    --concurrency 1 --warmup 5 --num_requests 32
# (with TLLM_PROFILE_START_STOP=12-24 exported), producing one report per rank.
```

To profile the reference **triton** sparse path instead of MSA, edit
`config.yaml`: set `sparse_attention_config.implementation: triton` and
`kv_cache_config.dtype: auto`.
